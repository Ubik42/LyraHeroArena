# 技术报告

## 目标

Lyra Hero Arena 不是把一个射击 Demo、若干性能脚本和一个编辑器面板拼在一起。它的目标是用同一真实多人项目回答三个问题：

1. 客户端 Gameplay 如何在 Lyra 既有边界内持续扩展；
2. 面对 200 个角色时，如何定位并证明一个具体优化；
3. 如何把一次性的 Profile 过程整理成可复跑、可比较的工程工具。

## Gameplay 架构

英雄选择是服务器权威状态。客户端提交英雄 ID，服务器校验后在 PlayerState 保存选择，并在 Pawn 初始化、死亡重生和换人时装配或撤销对应 AbilitySet 与装备。英雄能力继续使用 Lyra/GAS 的伤害、治疗、队伍和 TargetData 路径，模式规则不直接持有技能实现。

自有内容放在 `HeroArena` Game Feature 中。主工程只提供稳定的 Lyra 扩展点，避免英雄资产、模式资产与主模块形成双向依赖。C++ 负责权威规则、生命周期和网络边界，Blueprint 与 DataAsset 负责高频装配和表现。

## 性能实验合同

正式 A/B 必须固定：

- 引擎版本与源码提交；
- 地图、Experience、人数和随机种子；
- 分辨率、RHI、画质与固定镜头；
- 服务器/客户端拓扑；
- 预热时间、采样时间和原始数据路径。

Baseline 必须是合理可运行的实现，Optimized 只允许改变一个方向。每组结果至少比较三次运行的中位数和 P95，同时检查负载与质量。NullRHI 只用于逻辑和 CPU 隔离，不作为渲染结论。

### AI

AI 案例把相同的 Acquire / Chase / Engage 规则放在两种目标发现架构下比较：逐 NPC 全表扫描与共享空间分桶。衡量的不只是帧时，还包括候选检查数、目标查询时间、目标获取率和状态分布。

### Navigation

Navigation 使用确定性循环路线，记录请求、重规划、失败、到达、移动和持续卡住。全局预算虽然可以显著减少路径请求，但如果长时间未获服务的 Agent 增多，仍应判为失败。后续方案需要按等待时间和卡住风险提供公平性，而不是只调整预算数字。

### Animation / IK

动画方向接入 UE 官方 Animation Budget Allocator。近景和本地角色保持完整更新，远景角色允许降频与插值。性能结论必须与近景连续性、蒙太奇响应和姿态质量一起判断。

### Rendering

渲染方向使用正常 RHI 与固定镜头，分别测量 Game / Render / RHI / GPU、Draw Call、Primitive、阴影角色数和主要 Pass。角色阴影、附件、材质与距离剔除分别归因，不用综合开关替代单项结论。

## 性能工作台

`PerformanceLab` 是 Runtime 模块，负责压力、采样、元数据和质量 Guard；`PerformanceWorkbench` 是 Editor 模块，只负责编排与展示。两者通过 JSON 实验合同和结果文件连接，避免 Editor 依赖进入游戏运行时。

工作台不会自动宣称“优化成功”。它先检查样本是否可比较，再从同一提交和同一合同中选择完整的 Baseline 3 次与 Optimized 3 次。任何 Required Guard 失败，结果都不会进入正式比较。

## 边界

- 项目建立在 Epic Lyra 之上，不把 Lyra 原有能力描述为自研实现。
- 本仓库不分发 Epic 的地图、动画、角色、武器或其他二进制资产。
- 性能结果只适用于记录的硬件、版本、场景和合同；它们用于说明方法和归因，不是跨项目的普遍保证。
